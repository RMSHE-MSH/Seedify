# 提示词优化插件 · 需求与哲学定稿 v1

**日期**：2026-10-18｜**性质**：开发前定稿（哲学宪法 + 需求修订 + 工程约束）；未实现
**来源**：用户 2026-10-18 口述澄清 + 核心立场定稿文本；整合自第二、三轮调研报告（工作目录下同名文件）。

---

## 0. 本轮修订（用户澄清，优先于此前调研建议）

**R1 · 输入域收窄为纯文本。**
用户的消息经输入法语音转写后到达时**已经是文本**。插件只处理文本内容：不涉及音频、不涉及 ASR 识别、不需要 N-best 多假设解码。语音转写带来的同音错字（"帮窝"→帮我）依然在**文本层**处理——问题域是"转写文本的纠错与整理"，不是"语音识别"。

**R2 · L0 第一步的定义。**
对语音转写的文本进行**一定程度的纠正**，或对表达进行**优化和整理**，**提炼出用户真正的想法和意图**，整理好口语化的内容。
注意"提炼"的语义：从已有表达中抽取真实意图，不是补全想象——提炼 ≠ 发明。这与反臆造（病灶 3）一致。

**R3 · 工程约束：不依赖外界、轻量化。**
提示词优化是高频场景。若优化本身耗时长、耗 token 多，正式内容就无从谈起。因此：
- 插件本体 = 技能文本 + 至多极少辅助脚本，**零外部依赖为默认**（不装纠错库、不调外部 API、不引评测框架）；
- L0 一次通过、输出紧凑；优化器自身的输出也要克制（不写长篇诊断报告）；
- 外部工具（cap-evolve、pycorrector、claude-reflect 等）**全部移出范围**：纠错库不装（R3），L2/L3 机制不做（2.3 裁决）。

## 1. 核心立场（用户定稿 · 原文收录）

### 一、核心立场

反对"猜测派"，主张"实践派"。
我们明确反对"对话猜测式"提示词优化，它有三大病灶：

1. **过度约束 / 过拟合**——把软细节（流程、步骤、示例、格式）当硬约束预先写死；
2. **角色堆砌与铺垫**——"你是一位资深 X 专家……"式包装和冗长前言；
3. **臆造要求和细节**——优化器在对话里猜出用户从未说过的角色、业务背景、流程、例子。

立场的另一半：提示词优化不应压制 Agent 的自主性。Agent 的价值在于实践循环中建立理解、发现路径不对就自我修正、自我进化——过度具体的提示词会诱导它"照着执行"而不是"先思考再规划"，自主研究和自主设计的能力被预先夺走。

### 二、核心逻辑

1. **Agent 强在循环，不强在一次执行。** 它在实践中逐渐理解项目、修正路径，而不是照剧本演出。
2. **越具体的提示词，越是在替 Agent 做决定。** 细节写死之日，就是自主规划消亡之时。
3. **对话式优化没有真实信号，只能靠猜。** 让 AI 在聊天里"优化提示词"，它猜角色、猜流程、猜约束、猜例子——猜出来的东西看着完整，实则过拟合于它的想象，而非你的现实。
4. **优化必须发生在有反馈的系统里。** 真实信号（执行轨迹、评测集、真实纠错）→ 诊断为什么失败 → 改动 → 验证闸门（改动必须显著变好才保留，防回归）→ 保留或丢弃。这就是 GEPA、cap-evolve 们的方法论，也是"Prompt Engineering → Loop Engineering"的含义。
5. **约束要分家。** 硬约束（安全规则、验收标准）预先写死；软细节（流程、角色、示例）留给 Agent 在循环中长出来。过拟合的根源就是把软细节当硬约束。
6. **经验只从实践中来。** 被证实的教训才沉淀回记忆/技能，猜测永远不沉淀。

### 三、思路与核心哲学

一句话版本：**提示词是种子，不是蓝图；优化是进化，不是润色。**

四个哲学支点：
- **克制**——留白是功能，不是缺陷；
- **尊重主体性**——把 Agent 当会在循环中自我完善的合作者，而不是按单执行的工具；
- **证据主义**——每一条约束要有出处（真实纠错、评测证明），每一次优化要过闸门（held-out 显著性、防回归）。没有证据的细节不写，没有验证的改动不留；
- **诚实（避免幻觉）**——交集为空就报为空，不为凑数降标准、不臆造未核实的内容。这条对工具和对我们自己同样适用。

## 2. 需求规格（由定稿推出）

### 2.1 L0 单元：表达归一（插件第一功能）

**目标**：把口语化、带转写噪声的输入文本 → 干净的意图陈述（用户真正的想法）。

**输入**：任意自然语言文本（语音转写或手打）。
**输出**（紧凑三段，总预算约几百 token）：

```
【整理后】<干净意图陈述>
【改动】<逐处对照：原文片段→改动→类别（错字/赘词/指代/语序）>；无改动则省略本段
【待确认】<消歧问题，仅在确有歧义时列出；无则省略>
```

**处理范围（E1–E4）**：
- 错字/同音字/术语写法纠正（E1/E2）；
- 去填充词、去重复、断句、改口自纠解析（"不对，我是说 X"→X）（E3）；
- 指代消解、省略补全（标出推断）、歧义标注（E4）；
- **意图提炼**：从整理后的表达中抽出真实意图，写成一段平实的话。

**不处理（边界）**：
- 不发明用户没说的角色、背景、流程、示例、格式、验收标准（病灶 3 前置切断）；
- 目标/硬边界/验收的形式化属于 L1；L0 只交"干净意图"，缺验收项列入【待确认】而非编造。

**六原则（硬规则，每条配反例测试）**：
1. 纠错有据（保守；术语/代码标识符优先保原文；存疑并列候选）；
2. 信息零丢失（去赘不删义；改口留档）；
3. 消歧优先于臆断（问 > 保守解释 > 并列多解释）；
4. 重排不改义（可回指原文）；
5. 双输出可回溯（改动对照；可回退）；
6. 禁止增生。

**轻量执行方式（R3 落地）**：纠正与整理由**模型自身在技能规则下完成**，不挂外部纠错库；无脚本或仅一个极小辅助（可选）。pycorrector 等重型底座**不采用**（第三轮建议作废），仅在极端噪声场景由用户显式选择启用。

### 2.2 L1 种子化（第二功能，可与 L0 同次输出）

从干净意图提炼**目标 / 硬边界 / 验收标准**三项；软细节归零。缺项进【待确认】。
轻量化取舍：L0+L1 可**单次通过、两段输出**（整理结果 + 种子草案），人一次审完——保住了"人确认"闸门，又不增加交互轮次。此设计待开发阶段确认。

### 2.3 项目边界：L2/L3 不做（2026-10-18 裁决，公理 F）

**本项目止于种子化（L0+L1）。** 循环进化（L2）与经验沉淀（L3）是 Claude Code / Claude 桌面版 / cowork **内部 loop 已经实现的能力**——Agent 在实践中自我修正、把经验沉淀进记忆/技能。这不是我们要维护、要实现的内容；为 L2/L3 造机制（评测闸门、进化循环、沉淀框架）违反公理 F（边界公理）与自主公理。

种子与循环的关系是**接口契约**：种子必须交全目标/硬边界/验收三要素——**验收标准就是交给循环的反馈接口**（告诉循环怎么算完成/失败）。种子交对了，循环自己会长；种子交缺了，循环只能猜。

原"轻量/重仓两档闸门"方案随本裁决作废：插件内不设评测机制。L0/L1 自身的质量保障仅用**反例清单**（三大病灶 + 六原则的反例用例）做开发期自检，属实现细节不属运行时机制。

### 2.4 形态与触发

- 形态：一个轻技能（SKILL.md 为主），Claude Code / Claude 桌面版 / cowork 复用同一份技能文本，无 harness 专有依赖；
- 触发：自然语言（"帮我优化提示词"及语音变体"帮我优化提示**提**词"等——触发词本身要容错）；
- 性能预算：高频场景，优化一遍的 token 开销应显著小于"直接干活重来一遍"的开销；输出克制、不做长诊断（prompt-alchemist 式"🔍诊断报告+成品"为反例）。

## 3. 哲学支点 → 工程决策映射

| 支点 | 工程决策 |
|---|---|
| 克制 | L0 输出三段紧凑格式；无歧义不问、无改动不列；种子只留三项 |
| 尊重主体性 | 归一止于"干净意图"；流程/步骤/示例永不写入种子；循环与沉淀留给 Agent（公理 F） |
| 证据主义 | 每处改动标注类别与原文；每条沉淀规则附实践出处；硬规则配反例测试 |
| 诚实 | 调研结论如实（交集为空报为空）；【待确认】宁问不猜；文档标注未能核对项 |

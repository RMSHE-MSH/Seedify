# seedify（种子化）插件设计文档

**v6 · 2026-10-18 · 按需组件规划版**（组件逐类做需求判定，有用则上，不做一律归零）
**设计依据**：`prompt-optimization-charter.md`（**总纲 v4，用户定稿**，原文收录进插件）+ `prompt-optimization-spec-v1.md`（需求定稿，R1–R3）。
**一句话**：一个轻依赖的技能插件——把带转写噪声的口语输入，保真整理、问清疑问，自主生成种子提示词，只交付提示词本身。

---

## 1. 目标与范围

**做**：表达整理（总纲四·第一步）+ 种子提炼（总纲四·第二步，含提示词体检）。
**不做**（总纲四）：循环进化、评测闸门、经验沉淀、任务执行。提示词交给用户，循环归 Claude Code / 桌面版 / cowork。

## 2. 组件规划（按需判定）

原则：**真正有用的组件就上，没需求的给出判定理由，不做默认归零**；依赖尽量不引，优先主干实现。

| 组件类型 | 数量 | 用途 | 需求判定 |
|---|---|---|---|
| **Skills** | 1 | `seedify`：表达整理 + 种子提炼核心（触发短语自动激活，亦可斜杠调用） | 核心本体 |
| **Commands** | 2 | `/seed`：直接优化入口（免触发短语匹配，参数即原文）；`/seed-check`：提示词体检入口 | 真实高频入口——语音用户要少打字、要确定性入口；体检是日常把关需求 |
| **Agents** | 1 | `seed-reviewer`：独立体检员（新上下文对照纲领评审提示词，防同一上下文自我美化） | 体检需要独立视角；生成与体检分属不同上下文才有意义 |
| **Hooks** | 0 | — | 曾评估 UserPromptSubmit 自动提醒（疑似待优化输入未带触发词时提示）：违背总纲五"不执行未经委托的操作"，且逐条消息耗 token、误报噪声大。**留待真实需求出现再上**（若实际使用中"忘说触发词"高频，再加仅提醒不处理的钩子） |
| **MCP** | 0 | — | 用户方针：尽量不引外部依赖，优先主干实现。本插件功能无外部服务需求 |
| **Settings** | 0 | — | 无真实可配置参数；每一个多余旋钮都是机制膨胀（总纲五"精简"） |

**思想纲领入包**：总纲 v4 **原文**收录于 `references/charter.md`，SKILL.md 规定运行前先读——不改写、不缩写。

SKILL.md 篇幅不设指标，以说清规则为准。

## 4. 核心契约

### 4.1 输入

触发短语前后完整上下文中的自然语言文本（语音转写或手打）；`/seed` 调用时即参数。确无待整理文本时一行索要。

### 4.2 输出

**产出只有一样：优化后的提示词**——自然成文，置于代码块便于复制。

**有疑必问**：出现歧义、信息不完整、缺失项或任何疑问时，**先向用户提问，获取完整、准确的信息后再生成提示词**。提问次数不设限制——提问是了解任务全貌、获取信息的过程，其充分性优先；输出克制原则约束的是写入提示词的内容，不限制提问。用户明确表示不愿澄清时，作最保守理解，且不引入原文没有的内容。

**不输出**：对原文的改动对照、改动依据、整理过程说明、总结段。这些是内部检查项，不是交付物。

**种子的写法**：由工具**自主成文**，形式自由——一段、数行或一句均可。总纲三要素（目标、硬边界、验收标准）作为**提示**，不是栏位、不是模板：用户说到哪些写哪些，说到多少写多少，不为凑齐而补。不写实施方法（流程、步骤、角色、示例、格式），用户明确要求的除外。用户明确表示没有的要素，不写。

**内部纪律（执行但不输出）**：
- **可回指**：提示词的每一处修改都能在原文中找到依据；找不到依据的内容属于臆造，不得写入；
- **信息零丢失**：原文的语义成分不得在改写中消失。

### 4.3 体检契约（/seed-check → seed-reviewer）

**产出：诊断清单**——三大病灶逐项、软硬分家、目标与验收、可回指（若有原始意图）、自主空间；级别取"病灶/缺失/疑点"。只诊断不改写（改写须用户另行发起，走 seedify 技能）。独立上下文评审，不揣测用户未说的意图。

## 5. 运行流程（seedify 主流程）

```
触发 → 读 references/charter.md（领会核心思想）
     → 取原始文本
     → 表达整理（可回指、零丢失——内部约束）
     → 有疑否？（歧义 / 信息不完整 / 缺失项 / 任何疑问）
         有 → 开放提问（不限次数），问清后再继续
         无 ↓
     → 种子自主成文（三要素作提示，按实有内容写）
     → 交付提示词（代码块）；结束
```

用户补充信息或要求修改时，从表达整理重走。

## 6. 表达整理规则（总纲四·第一步落地，内部执行）

1. 纠错有据：转写错字按音/上下文保守纠正；术语与代码标识符优先保原文；存疑即问。
2. 信息零丢失：只删无语义填充；改口以最终说法为准。
3. 消歧优先于臆断：有歧义一律先问；禁止选"最丰富的解释"。
4. 可回指：每一处修改都有原文依据；无依据即臆造，不得写入。

## 7. 种子提炼规则（总纲三·L1 + 四·第二步落地）

种子**自然生成**：工具按任务自主成文，不套格式。三要素仅作提示性考虑——目标、硬边界、验收标准——用户表达中有什么就写什么，不为凑齐而补。任何要素缺失或存疑 → 按 §4.2 先问后写；用户明确表示没有的则不写；不代拟、不编造。成文后自检：可回指吗？写了实施方法吗？为凑内容添了东西吗？

## 8. 触发设计

- 显式触发短语写入技能 description："帮我优化提示词 / 优化提示词 / 提示词种子化 / seed prompt / 整理我说的话 / 把这段变成提示词"；
- 语音变体容错：description 注明触发短语可能含转写错字（"帮我优化**提**词""帮窝优化提示词"），按音近语义识别；
- 命令入口：`/seed`（直接优化）、`/seed-check`（体检）——确定性入口，免触发匹配；
- 不自动触发：输入再嘈杂，无触发短语与命令不动；
- 边界消歧：触发后内容若本身是个任务而非待优化提示词，回一行问清。

## 9. 开发期验收：测试清单

| # | 测什么 | 用例要点 | 通过标准 |
|---|---|---|---|
| T1 | 禁增生 | 只说了一句要做什么 | 提示词不得含角色/流程/示例/风格 |
| T2 | 零丢失 | 原文含一处具体细节 | 提示词必须保留 |
| T3 | 改口解析 | 原文中途改口两次 | 以最终说法为准（对照不输出） |
| T4 | 宁问不猜 | 意图含糊 | 先提问，不臆造，问清后生成 |
| T5 | 输出纯净 | 任意输入 | 只有提示词；无改动对照、无依据、无整理段、无总结 |
| T6 | 缺项必问 | 无验收无边界 | 先开放提问补全信息后写入；用户说"没有"则不写；不编造 |
| T7 | 触发容错 | 触发短语含转写错字 | 仍正确触发并归一 |
| T8 | 交付即止 | 正常输入 | 输出提示词后不自动开工 |
| T9 | 转写纠错 | 含同音错字 | 提示词中已纠正 |
| T10 | 输出克制 | 任意输入 | 无长诊断、无报告 |
| T11 | 可回指 | 任意输入 | 提示词每处都能对应原文依据 |
| T12 | 自然生成 | 只说了一句目标 | 提示词就是一句，不补边界与验收，不套格式 |
| T13 | 提问充分 | 多处信息缺失 | 允许多轮提问直至信息完整，不设次数上限 |

体检类补充验收：`/seed-check` 对带病灶提示词（角色堆砌/软细节写死/臆造）能逐项指出，对干净提示词明确"未发现病灶"且不改写。

## 10. 明确不做

- ✗ 输出改动对照、改动依据、整理过程、总结段
- ✗ 正例/反例进技能上下文（少样本锚定）
- ✗ 填空模板式提问
- ✗ 对提示词生成设提问次数、篇幅、Token 等硬性指标（元层面过约束）
- ✗ 自动钩子预处理一切输入（未经委托不操作）
- ✗ 评测/进化/沉淀机制（总纲四）
- ✗ 外部纠错库、API、MCP、脚本管线
- ✗ 输出后自动开工
